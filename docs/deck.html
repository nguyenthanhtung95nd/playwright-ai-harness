A personal journey into AI-tested automation

The Playwright AI Harness

How a small, disciplined AI harness lets any engineer own the test quality for their own feature.

01 · The Cost

When a test suite stops being trusted

  • A failure shows up. The first question isn't "what broke," it's "is this even real?"
  • Once that question is routine, the suite has been demoted from safety net to background noise.
  • It isn't a tooling problem. Playwright, Cypress, Selenium: it doesn't matter which. Nobody wrote down what a good test is allowed to do.
  • Once an AI agent is writing the tests, that written discipline is the only thing standing between "the agent said it's done" and "it's actually done."

02 · The Mindset

Shift left, or inspect the house after it's built

Testing was traditionally a siloed activity done after development. Full stack testing begins in parallel with development and runs through the whole delivery cycle. That's shift-left testing.

The payoff: before shifting left, a team gets all its feedback after development is "done." After, roughly half of that feedback arrives before the story even reaches the testing phase.

Quality is the team's responsibility: performing these checks at every phase has to be owned by every role on the team, not just testers or QA. Building the relevant testing skill is everyone's job.

  • That's the premise this whole harness rests on: if quality is everyone's job, the rules for a good test have to be written down and portable to everyone, not kept in one QA engineer's head.

03 · The Definition

Two things. Nothing more.

Part one

One mindset document

The handful of non-negotiable rules a reviewer would enforce by hand anyway: how tests get their data, how they wait, where assertions may live.

Part two

A few lifecycle playbooks

Plan, build-and-verify, ship: repeatable sequences the agent follows, not fresh instructions typed every time.

Context engineering: an agent only behaves as well as the information in front of it at the moment it decides something. Nothing written down, nothing loaded, doesn't exist for that run.

External reinforcement loop: left alone, an agent's incentive is to report success. A test, an audit, a git hook: something outside its own judgment it cannot talk its way past.

  • The harness is not the rules file by itself. It's the rules file plus something automatic that checks whether the rules were followed.

04 · Rules vs Skills

Two parts, two different loading rules

Part one and part two from the last slide don't just differ in content, they differ in how an agent even gets access to them.

Rules

Always in context

A rule file loads into every single conversation automatically, whether this turn needs it or not. That's why the mindset document has to stay short: nothing can start a test without it already loaded.

Skills

Loaded on demand

A skill is discovered by its own description when the task matches, or invoked by name on purpose. The lifecycle playbooks live here, so a conversation that isn't planning or shipping a test never has to carry their full detail.

A skill is not a prompt template: it bundles domain knowledge with a repeatable workflow. That's why pw_plan, pw_work, and pw_setup are multi-step documents with named modes, not one-line instructions.

And there's a third layer, below both: permissions. .claude/settings.json in this repo denies git commit and git push outright. A rule can be reasoned around; a denied permission cannot.

  • Not everything an agent might need belongs in every conversation. Rules are the floor that's never optional. Skills are the toolbox reached for only when the job calls for it.

05 · The Test Pyramid

The shape isn't a matter of taste

One line of strategy: test the right scope of functionality at the layer that gives the team the fastest feedback. As scope grows, each test costs more to write, run, and maintain, so the shape has to taper.

Run the arithmetic on your own suite: a unit test finishes in milliseconds. A UI-driven test that logs in, navigates, and waits on real network round trips takes 30 to 90 seconds. Two hundred of those is a nightly job, not a feedback loop. The same coverage proved one layer down finishes before the coffee does.

Not always possible: missing test environments, tooling gaps (e.g. barcode scanning), or the right skills can make the ideal pyramid impractical. When that happens, be deliberate about the trade-off, not silent about it.

06 · Antipatterns

Two ways the pyramid breaks, and AI makes both worse

Both of these are easy to fall into when an agent can generate a dozen tests in a minute. The speed is real; so is the fact that neither failure mode announces itself. Watch for the early symptoms instead.

Invert the pyramid

The ice-cream cone

Symptoms: long waits for feedback, defects caught only during release testing, elaborate manual testing despite having "automation," and frustration with tests that don't produce the right results.

Duplicate the pyramid

The cupcake

Usually surfaces when developers and testers work in silos, each adding the same case at their own layer. AI-assisted bulk generation increases the odds of this happening, because it's fast to generate coverage without checking what already exists.

Earliest tell of the ice-cream cone: finding regression defects during manual story testing. Root-cause it immediately, before the problem compounds.

Fix for the cupcake: bring developers and testers together, ideally at story kickoff, to decide which layer owns which test case, and write that decision on the story card.

  • This is exactly why "could a lower layer prove this cheaper?" is the first question in our pyramid gate: not a style preference, a defense against both of these.

07 · Autonomy Has a Floor

Even told to work autonomously, some steps don't skip

All three skills in this harness open with the same line, verbatim. It is the first instruction the agent reads, before any mode is chosen. 

# .claude/skills/pw_plan/SKILL.md, pw_work/SKILL.md, pw_setup/SKILL.md

**Never skip `AskUserQuestion` steps in this skill,
  even if told to work autonomously.**

Plan before anything is written

Read-only until a human approves

pw_plan's first instruction is to enter plan mode. It reads the existing specs and the app source, brainstorms cases, and writes no file at all until the plan itself is approved.

Ship never means commit

The hard rule, stated twice

pw_work's SHIP mode stages the change and drafts a message. It never runs git commit or git push, in any mode, even if the user says yes to a commit prompt. A human runs that line themselves.

  • The checkpoint lives in the instructions, not in the agent's judgment about whether pausing is worth it. "Just get it done" can't dissolve it.

08 · Debugging Discipline

Three debuggers, one rule

pw_work's VERIFY mode carries three debug branches, split only by where the evidence comes from. All three converge on the same first move before any code is touched.

EVIDENCE: SAVED TRACE

Local failure

Run the failing test with tracing forced on, then read the trace through the command line, never the blocking GUI viewer.

EVIDENCE: LIVE PAGE

Race or timing bug

Pause a running test at an exact line, then probe the live, paused browser directly when a static trace alone can't explain it.

EVIDENCE: CI ARTIFACT

Only fails in CI

Pull the trace out of the failed workflow run and treat it as the authoritative record, not a local re-run that may not even reproduce it.

Before fixing anything: name which bucket the failure is in. Test bug, application bug, environment or config problem, or flake.

Never paper over it: a flake or an application bug doesn't get fixed with a longer timeout, a retry, or force: true. That just hides it from the next person who hits it.

09 · Audit Discipline

A fresh session, scoped to what actually changed

VERIFY's audit branch runs deliberately as a new session, with no memory of having written the code it is reviewing.

Scope

The uncommitted diff, nothing else

No uncommitted changes means nothing to review: stop. A test that's already committed doesn't get silently re-opened by this pass.

Posture

Fresh eyes, cited rules

The reviewing agent is explicitly told it is not the agent that wrote the code, and to question every choice. Every finding cites the specific rule it violates. An opinion with no rule behind it doesn't belong in the report.

Severity, not a wall of red: findings split into must-fix, should-fix, and suggestions, plus a "what looks good" section, so the report reinforces what was done right too.

Define done before the agent starts: an autonomous fix only works when "done" was stated up front. Here it's exact, and it's the same command every time, so there's nothing for the agent to interpret: npx playwright test -g "<title>" --retries 0 passes, and nothing else broke.

  • Same posture as Pillar 1: the rule wins the argument, not the agent's opinion of its own work.

10 · The Skills Ecosystem

Two copies of the same skill, one precedence rule

pw_setup's SHARE and SYNC modes exist because of one fact about how Claude Code resolves skills.

On your machine

Personal always overrides project

If a skill with the same name exists both in your personal setup and in a project, your personal copy runs. Always. Pushing a copy into the project does not change that.

For everyone else

The project copy is for them

Teammates without your personal setup, and CI machines with no personal copy at all, get the project version. That is the entire reason SHARE exists.

When the two drift: SYNC does not auto-merge. For every item that differs, a human picks which side wins, project overwrites personal or personal overwrites project, one at a time.

  • The same judgment-over-automation stance as the rest of this harness: a human decides, the tool never guesses.

11 · Pillar One

Judgment over compliance

Four places where this harness is deliberately stricter than the default advice most teams have absorbed. Each one trades convenience for a specific defect class it refuses to let through.

01 · Retries

Common guidance

Judicious retries are an acceptable bandage for genuinely flaky, transient failures.

Trades short-term green builds for hidden race conditions.

VS

What we enforce

retries: 0. A flaky pass is a defect report, never smoothed over.

Any retry gives the next race condition a place to hide.

02 · Test data

Common guidance

Database-backed data pools are legitimate for expensive or finite test data.

A pool proves the DB accepts rows, not that the app's own write path works.

VS

What we enforce

No direct database writes: every row comes from a real user flow.

Catches the app's own create-path breaking silently.

03 · Locator strategy

Common guidance

Dedicated test-id attributes rank above semantic / role-based locators.

A test-id can point at the right pixel while hiding a broken accessible name.

VS

What we enforce

Role- and label-based locators only: a missing accessible name is a defect.

The locator strategy doubles as a continuous accessibility check.

04 · Self-healing locators

Common guidance

AI-assisted self-healing locators are a meaningful reliability improvement.

Optimizes for the test staying green, even pointing at the wrong element.

VS

What we enforce

Locator ambiguity is flagged for a human, never auto-healed.

Optimizes for the test staying honest, not just green.

12 · Network Determinism

Record once, replay exactly

The discipline Pillar 1 argues for locators and test data applies one layer down, to the network: capture what really happened, then replay it exactly. Codified in .claude/rules/playwright-scripting.md.

Record — once, with the real service reachable

await page.routeFromHAR("e2e/.har/articles.har", {
  url: "**/api/articles**",
  update: true,          // writes the archive from this run
})

Replay — every run after

await page.routeFromHAR("e2e/.har/articles.har", {
  url: "**/api/articles**",
  update: false,         // same response, service up or not
})

Or capture it straight from a browser, no test needed

# BASE_URL comes from .env.test.<env> -- never a hardcoded host
npx playwright open --save-har=e2e/.har/articles.har "$BASE_URL"

Not the same as mocking: a recorded archive is something that actually happened. Scope url to the endpoints the test depends on: a HAR that captures fonts, analytics, and images is slow to replay and breaks on changes that have nothing to do with the test.

Intercept only what a real run can't produce: a 500, a timeout, an empty list. Never intercept the app's own create-path to fake test data, that's the one check Rule 4 exists to protect.

13 · Pillar Two

Lean beats sprawling

The obvious way to add capability to a harness is to add another skill file. Every one of those is a new thing a person has to remember exists and choose correctly between. Depth belongs inside a workflow instead.

The entire harness — 3 skills, 7 modes, 10 branches

pw_plan    plan mode → researched coverage plan → .claude/pw-plans/

pw_work    IMPLEMENT   new test | refactor into page objects
           VERIFY      audit | debug: trace | live attach | CI artifact
           SHIP        stage + draft message  (never commits)

pw_setup   INIT | SHARE | SYNC

One skill per action

Ten-plus entry points

A separate file for each debug scenario, each generation case, each setup task. Someone has to pick the right one every time, and the files drift out of sync with each other.

One skill per lifecycle stage

Three entry points, same depth

You pick by where you are in the work — planning, building, setting up — which you already know without being told. The branching happens inside, where it costs nobody anything.

Count the things a person must choose between, not the capabilities: depth inside a mode is free. A new file at the top level is not. Skill count is a cost, not a feature.

Pillar 2 made the case in the abstract. This is the same lesson on a concrete ticket: one plan, three modes, and exactly one place where a human has to act.

15 · Live Demo

Three checkpoints, one unfamiliar app

Everything from here happens on a public demo app none of us have touched. If this only worked on a familiar project, it wouldn't prove anything.

CHECKPOINT A

Init Rules

Write the mindset document from a blank slate, out loud. If it needs more than a page or two, the architecture is probably hiding something the rules shouldn't have to cover.

CHECKPOINT B

Coverage Plan

Before any test code exists, produce a plan you could reject in two minutes, including what should NOT be an E2E test because a cheaper layer already proves it.

CHECKPOINT C

Audit (+ git hook)

Run the audit against a test that deliberately breaks a rule. If time allows: the same check wired into a pre-commit hook (Husky + lint-staged), now it's a gate, not a step someone can skip.

16 · How to Get Started

Two real files, not a concept

testing-mindset.md and the three pw_* skills already exist in this repo. Installing them into your own project is one skill, run once.

RULE

testing-mindset.md

The actual file enforced in this repo: pyramid gate, locators, waiting, test data, flakiness, assertions, independence, enforcement, each with a stated why, not just a rule.

pw_setup · INIT

Scaffold a new framework

Installs Playwright, config, directory structure, and the rule file in one pass, for a project that has none of this yet.

pw_setup · SHARE

Commit the skills for your team

Copies pw_plan, pw_work, and pw_setup itself from your personal setup into the project, so teammates and CI get the same workflow.

pw_setup · SYNC

Keep both sides honest

Reconciles drift between your personal copy and the project's, one item at a time, your call on which side wins.

Run it once, in your own project

> /pw_setup

# It asks, and waits for your answer, before writing anything:
  How many test environments, and the baseURL for each?
  Which auth roles?  guest | user | admin | ...
  Explore the source for the login flow, or shall I use placeholders?
  Wire a mechanical audit into a pre-commit hook?

# Then it writes:
  e2e/                     specs, one folder per role
  playwright.config.ts     one project per role, retries: 0 locally
  playwright-utils/        fixtures, helpers, pages, .auth/

  .husky/pre-commit        the gate (if you said yes)

Same three skills either way: brand-new project or one that already has tests. INIT scaffolds, SHARE commits the skills for your team, SYNC reconciles the two copies when they drift.

17 · How to Get Started

One ticket, three skill calls, start to finish

This is the whole loop, typed out. Nothing is paraphrased — these are the actual invocations and what comes back from each. 

# The ticket you were handed
#   CON-412 -- a signed-in user can favorite an article from the
#   global feed, and the favorite count goes up by one

> /pw_plan a signed-in user favorites an article from the global feed

  → enters plan mode (read-only -- writes nothing yet)
  → reads e2e/**, src/app/features/article/**, testing-mindset.md
  → returns P0/P1/P2 cases, plus what should NOT be an E2E test
  → you approve → .claude/pw-plans/favorite-article-from-feed.md

> /pw_work implement the first P0 case from favorite-article-from-feed

  → reads the plan, the existing specs, the component source
  → writes e2e/user/favorite.spec.ts
  → asks before running, then: playwright test -g "..." --retries 0

> /pw_work verify

  → fresh-eyes audit, scoped to git diff HEAD and nothing else
  → must-fix | should-fix | suggestions | what looks good
  → every finding cites the rule it violates

> /pw_work ship

  → stages the change, drafts the commit message
  → stops. You run git commit yourself.

You don't have to name the mode: "debug this failing test" goes straight to VERIFY's debug branch, "refactor these into page objects" goes to IMPLEMENT's branch B. The skill states which mode it picked before it acts, so you can correct it.

18 · How to Get Started

Log in once, reuse the session everywhere

pw_setup already does this, it just hasn't been said out loud yet.

The problem

Logging in on every test is slow and brittle

A real login flow through the UI, repeated for every single test, multiplies run time and multiplies the chances of the login flow itself breaking the thing it wasn't even testing.

The fix, already built

storageState, generated once per role

pw_setup's INIT mode writes auth.setup.ts and saves storageState per role, run once as its own project with everything else depending on it. Swapping to a different role for one test is a config change, not a rewrite.

e2e/auth.setup.ts — runs once

setup("authenticate as user", async ({ page }) => {
  await page.goto("/")
  await page.getByRole("link", { name: "Sign in" }).click()
  await page.getByRole("textbox", { name: "Email" })
    .fill(process.env.USER_EMAIL!)
  await page.getByLabel("Password")
    .fill(process.env.USER_PASSWORD!)
  await page.getByRole("button", { name: "Sign in" }).click()
  await page.waitForURL("**/")
  await page.context().storageState({ path: userFile })
})

playwright.config.ts — every test reuses it

projects: [
  { name: "auth-setup", testMatch: "auth.setup.ts" },
  {
    name: "user",
    testDir: "./e2e/user",
    use: { storageState: "playwright-utils/.auth/user.json" },
    dependencies: ["auth-setup"],
  },
  {
    name: "guest",
    testDir: "./e2e/guest",
    // no storageState -- unauthenticated on purpose
  },
]

Credentials and URLs never appear in a test. They come from .env.test.<env>, which is gitignored, and every test navigates with relative paths so baseURL stays the one place an environment is named.

19 · How to Get Started

Two ways to get a locator you didn't guess

Rule 2 says never guess a locator. These are the two tools that mean you never have to — one when you can read the app's source, one when you can't.

Codegen — perform the flow once, get a draft back

# Records every click and fill as you do it, emits test code live
npx playwright codegen "$BASE_URL"

# Start from a signed-in session instead of the login page
npx playwright codegen \
  --load-storage=playwright-utils/.auth/user.json "$BASE_URL"

The CLI — when the app's source isn't yours to read

npx playwright-cli open "$BASE_URL"
npx playwright-cli snapshot            # roles + names + refs
npx playwright-cli click <ref>
npx playwright-cli generate-locator <ref>   # ask, don't guess
npx playwright-cli close

Both outputs are drafts, not tests. Codegen happily emits a CSS chain. pw_work's IMPLEMENT mode re-checks every locator against the priority order — role, label, text, placeholder, testid, and only then CSS — and replaces what doesn't hold up.

If no semantic locator exists: when the source is yours, the fix is a data-testid added to the component, not a class selector. When it isn't, the skill flags it so you can ask the owning team for one.

20 · How to Get Started

When it goes red, name the bucket first

The temptation is to make the red go away. The rule is to find out what the red is telling you — and the evidence is already on disk. 

> /pw_work debug "User can favorite an article from the feed"

# 1. Re-run it: tracing forced on, retries off
npx playwright test -g "User can favorite an article..." --trace on --retries 0

# 2. Read the trace from the CLI -- not the GUI viewer, which blocks
npx playwright trace
  open test-results/<dir>/trace.zip
  actions --grep="expect"    # find the step marked with an X
  action 14                  # what it tried, what it got
  snapshot 14 --name after   # the DOM at that instant
  requests                   # did the API call even fire?
  console                    # did the app throw?
  close

# 3. Before touching any code, say which one it is:
   test bug  |  application bug  |  environment/config  |  flake

Two other branches, same first move: when a static trace can't explain a race, VERIFY pauses the live run at an exact line and probes the real page. When it only fails in CI, it pulls the trace out of the failed workflow run with gh and treats that as authoritative, not a local re-run that may not reproduce it.

What never counts as a fix: a longer timeout, a retry, or force: true on an application bug or a flake. That just hides it from whoever hits it next.

A rule only checked by memory is a hope

Rule 8 is the one that makes the other seven real. Anything checkable mechanically gets checked mechanically — pw_setup wires this up, and asks you which rules to include.

e2e/audit.mjs

const CHECKS = [
  {
    rule: "Rule 3 -- Waiting",
    pattern: /waitForTimeout\s*\(/g,
    message:
      "Fixed wait found. Use a " +
      "web-first assertion instead.",
  },
  {
    rule: "Rule 4 -- Test data",
    pattern: /\b(INSERT INTO|db\.collection\()/g,
    message:
      "Direct seeding. Create data " +
      "through the app's own flow.",
  },
]

.husky/pre-commit

npx lint-staged
node e2e/audit.mjs

# A non-zero exit blocks the commit.
# Not a review step someone skips
# under deadline pressure -- a gate.

Every finding cites the rule, the file, the line, and the offending code — never an opinion.

Be honest about the gap: two of the eight rules have a mechanical check today. "One behavior per test" and "could a lower layer prove this cheaper" have no reliable pattern, so they stay review-only. That gap is the backlog — and the rule file says so about itself, rather than pretending the other six are covered.

Take This With You

Field Checklist

Pin this next to your editor. Printing this page (Ctrl/Cmd+P) from anywhere in this deck prints only this one-page handout.

Before adding any test, ask: could a unit or component test prove this cheaper? E2E is for journeys that cross a real boundary (routing, auth, API, storage), not for validation or pure logic. If a lower layer could catch it, it does not belong here.

01 · LOCATORS

Role and label first

Never guess a locator. A missing or ambiguous accessible name is a defect in the app, not a reason to fall back to a CSS selector.

02 · WAITING

No fixed waits, ever

Web-first assertions and condition-based waits only. A sleep encodes one machine's timing and breaks on the next.

03 · DATA

Real flows, not seeding

Every record comes from the app's own create-path. Seeding a database proves the database works, not the app.

04 · FLAKINESS

retries: 0

A test that fails then passes on retry is a defect report about a race condition, not noise to smooth over.

05 · ASSERTIONS

Structural, one behavior

One behavior per test. Assert generated or timestamped content structurally, never on exact rendered text.

06 · INDEPENDENCE

Own identity, any order

Every test runs alone and in any order. No test may depend on state another test left behind.

07 · ENFORCEMENT

A hook, not a hope

A rule only checked by memory is not a rule. Wire what can be checked mechanically into an audit or a commit hook.
